# otchetTK — автоматизированная экспертиза технологических карт (MVP)

Прототип системы автоматизированной экспертизы технологических карт (ТК)
технического обслуживания авиационной техники с применением большой
лингвистической модели (LLM). Реализован по техническому заданию
[otchetTK.md](otchetTK.md).

Прототип — **автоматический рецензент первого прохода**: он формирует перечень
замечаний с привязкой к тексту ТК; окончательное решение принимает эксперт-человек.

## Что проверяется (рубрикатор)

| Рубрика | Содержание проверки |
|---|---|
| Р-1 Последовательность | Парные операции («открыл — осмотрел — закрыл»), порядок операций, разрывы последовательности, завершающие операции |
| Р-2 Визуализируемость | Текст шага должен «рисовать картинку и действие в голове»: одно действие на шаг, конкретные глаголы, локализация объекта, количественные параметры, отсутствие неопределённых местоимений; реконструкция действия моделью |
| Р-3 Меры безопасности | Ссылки на пункты мер безопасности РЭ по затронутым системам; ключевые маркеры (обесточить, заземлить, стравить давление, заблокировать, зашвартовать, поставить колодки и т. п.) перед критическими операциями; отсутствие перегрузки ТК дублированием мер |
| Стиль | Сопоставление с эталонными картами: структура шага, глагольные формы, детализация, оформление ссылок |

Результат — отчёт `.md` (для эксперта) и `.json` (для интеграции). Каждое
замечание содержит рубрику, критичность, дословную цитату (программно
проверенную на присутствие в тексте ТК — защита от галлюцинаций), обоснование
и рекомендацию. Отдельный раздел «Не проверялось» перечисляет проверки,
которые выполнить не удалось.

## Установка

Требуется Python 3.11+.

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

## Настройка LLM

Этап MVP — внешний OpenAI-совместимый API (см. `config.yaml`). Ключ задаётся
переменной окружения, в репозитории не хранится:

```bash
export OPENAI_API_KEY="ваш ключ"
```

В систему на этапе MVP загружаются только обезличенные/учебные ТК без сведений
ограниченного распространения (ТЗ, п. 6.1).

**Переход на локальную модель с открытыми весами** (Qwen, Llama, Mistral и т. п.
через Ollama/vLLM) выполняется только сменой конфигурации — см.
`config.local.yaml`. Код проверок не меняется.

## Запуск экспертизы

```bash
.venv/bin/python -m otchettk data/test_cards/tk_102_defects.docx
```

Параметры:

```
python -m otchettk <файл ТК .pdf|.docx> [--config config.yaml] [--out каталог]
                   [--safety-base каталог] [--etalons каталог]
```

Отчёты записываются в `reports/`, журнал запуска (все запросы/ответы LLM,
отброшенные замечания) — в `logs/run_<время>/`.

## Базы знаний (пополняются добавлением файлов, без изменения кода)

- `data/safety_base/` — меры безопасности при работе на авиационной технике
  (выписки из РЭ, `.pdf`/`.docx`). Каждый документ автоматически
  структурируется моделью (звено П-Б) и кэшируется по хэшу файла.
- `data/etalons/` — эталонные ТК (образцы стиля изложения). Рядом с каждым
  файлом можно положить метаданные `<имя>.meta.json`:

```json
{"title": "…", "work_type": "осмотр, проверка", "system": "электросистема", "added": "2026-09-02"}
```

## Архитектура: цепь промптов

```
ТК (.pdf/.docx) -> извлечение текста
  П-0 структуризация -> П-1 контекст работ
  -> параллельно: П-2 (Р-1), П-3 (Р-2), П-4 (Р-3, по базе мер), П-5 (стиль, по эталонам)
  -> П-6 агрегация и дедупликация
  -> программная верификация цитат (без LLM)
  -> отчёт .md + .json
```

Шаблоны промптов — в каталоге `prompts/` (правятся без изменения кода).
Каждое звено возвращает JSON, валидируемый по схеме (`otchettk/schemas.py`);
невалидный ответ перезапрашивается (не более 2 повторов), затем звено
фиксируется в разделе отчёта «Не проверялось». Температура генерации — 0.

## Тестовые данные

Каталог `data/test_cards/` (все документы учебные, обезличенные):

- `tk_101_correct.docx` — корректная ТК (ожидание: без критических замечаний);
- `tk_102_defects.docx` — ТК с 5 внесёнными дефектами (электросистема);
- `tk_103_defects.pdf` — ТК с 5 внесёнными дефектами (гидросистема), PDF с текстовым слоем;
- `defects_etalon.md` — эталонный перечень внесённых дефектов для оценки полноты
  обнаружения (критерий приёмки 2).

Тестовые документы пересоздаются скриптом:

```bash
.venv/bin/python scripts/make_test_data.py
```

## Офлайн-демонстрация без внешнего API

Полный конвейер можно прогнать без внешних сервисов — на локальном
сервере-заглушке с заготовленными ответами (демонстрирует и смену провайдера
только конфигурацией):

```bash
.venv/bin/python scripts/mock_llm_server.py &
.venv/bin/python -m otchettk data/test_cards/tk_102_defects.docx --config config.demo.yaml
```

## Автотесты

Механика цепи (валидация, повторы, агрегация, верификация цитат, базы знаний,
отчёты) покрыта тестами на фиктивном LLM-провайдере — внешние API для тестов
не нужны:

```bash
.venv/bin/python -m pytest tests/ -v
```

## Структура репозитория

```
otchetTK.md          техническое задание
otchettk/            пакет прототипа (CLI: python -m otchettk)
prompts/             шаблоны промптов П-0…П-6, П-Б
data/safety_base/    база мер безопасности (пополняемая)
data/etalons/        база эталонных карт (пополняемая)
data/test_cards/     тестовые ТК и эталон дефектов
scripts/             генерация тестовых данных
tests/               автотесты (фиктивный провайдер)
config.yaml          конфигурация MVP (внешний API)
config.local.yaml    пример конфигурации локальной модели
```

## Ограничения MVP

Не входит (ТЗ, раздел 9): графический интерфейс, OCR сканов, векторный (RAG)
поиск, проверка фото-/пооперационного контроля, интеграция с документооборотом,
работа с документами ограниченного распространения (до перехода на локальные
модели).
