# Оценка реализуемости: система цифровых паспортов авиационных агрегатов

**Вердикт:** проект **реализуем**. Сложность сосредоточена не в «фото → текст», а в надёжном сопоставлении повторных сканов, аудите изменений и правилах контроля ресурса/срока службы. Ниже — оценка по блокам на основе образца паспорта МГВ-1СУ8 (документ `6В2.564.002-4ПС2`, зав. № `1160340`, 1976). Автономная работа на изолированном ПК без Интернета — целевой режим поставки.

---

## 1. Что видно по образцу документа

Типичный бумажный паспорт авиаагрегата советского/постсоветского образца:

| Поле | Пример | Тип данных |
|------|--------|------------|
| Наименование | Малогабаритная гировертикаль | печатный текст |
| Модель / индекс | МГВ-1СУ8 | печатный + возможна рукопись при модернизации |
| Код документа | 6В2.564.002-4ПС2 | печатный (стабильный шаблон) |
| Заводской № | 1160340 | **рукопись** |
| Год | 1976 | смешанный (19 + рукопись) |
| Отрывной корешок | дубль полей | тот же набор |

Особенности, влияющие на архитектуру:

- жёсткая компоновка страницы (верх / линия отреза / корешок) — удобно для шаблонного каркаса OCR;
- рукописные поля (номер, год) и возможные дописки — нужен ICR / vision-слой плюс ручной ввод оператора;
- на живых экземплярах встречаются **печати и подписи** должностных лиц — это уже не чистый шаблон, а детектирование графических реквизитов;
- при модернизации меняется наименование/индекс, **заводской номер остаётся ключом идентичности**.

Аналогия из запроса (штрих-код) верна: распознавание — ускоритель, **оператор — источник истины** при сомнении.

## 2. Архитектура системы (логические блоки)

```
[Фото паспорта]
      │
      ▼
[Предобработка] → [Гибрид: шаблон + OCR/ICR + vision-ИИ] → [Извлечение полей]
      │                                                         │
      ▼                                                         ▼
[Карточка цифрового паспорта] ←──────── [Оператор: подтверждение / правка]
      │
      ▼
[Реестр агрегатов ВС] ←── [Журнал изменений + наработка]
      │
      ▼
[Правила / аналитика] → [Подсветка рисков] → [Рекомендации]
```

### 2.1. Распознавание (OCR / ICR / vision)

**Возможность: высокая** при **гибридном** конвейере: шаблонный слой преобладает на структурированных печатных полях, а гибкие модели (ICR и multimodal / document-vision ИИ) закрывают то, что шаблоном не описывается — свободную рукопись, печати, подписи должностных лиц.

Шаблонный подход здесь — не отказ от ИИ, а **якорь геометрии бланка**. Универсальный «ИИ на всё фото целиком» без шаблона хуже контролирует обязательные поля и уверенность по зонам; наоборот, один только шаблон ломается на живом документе с заверительными реквизитами. Нужны оба контура.

#### Что встречается на реальных паспортах

| Слой документа | Примеры | Как распознавать |
|----------------|---------|------------------|
| Печатная структура бланка | «ПАСПОРТ», код `6В2.564.002-4ПС2`, линия отреза, корешок | шаблон + печатный OCR |
| Структурированные поля | наименование, индекс, зав. №, год | ROI по шаблону + OCR/ICR |
| Свободная / полусвободная рукопись | пометки о модернизации, даты работ, записи в графах учёта | ICR + document-vision; низкая уверенность → оператор |
| Печати / штампы | круглая печать завода, ОТК, войсковой части | детекция печати как объекта + OCR текста в оттиске (где читаемо) + факт «печать есть / тип / зона» |
| Подписи должностных лиц | приёмка, контроль, изменение | детекция зоны подписи (наличие, положение); расшифровка ФИО — только если рядом есть читаемый текст или отдельное поле; биометрическая верификация личности **не цель MVP** |

#### Рекомендуемый конвейер

1. **Предобработка:** выравнивание перспективы, нормализация освещения, подавление бликов; отдельные ветки обработки для текста и для цветных оттисков печатей.
2. **Классификация типа бланка** (семейство паспортов: МГВ и др.) по печатным якорям (`ПАСПОРТ`, код `*ПС*`, линия отреза) — шаблонный слой.
3. **Зоны интереса (ROI)** по шаблону: наименование, индекс, код ПС, № изделия, год, плюс **зоны реквизитов** (места предполагаемых печатей и подписей на данном типе бланка).
4. **Печатный OCR** (PaddleOCR / Tesseract с кириллицей или коммерческий SDK) — стабильные печатные поля.
5. **Рукопись (ICR):** заводской номер, год, пометки в графах; при низкой уверенности поле подсвечивается для ручного ввода.
6. **Слой vision-ИИ (дополнение к шаблону, не замена):**
   - поиск и классификация **печатей** вне жёсткой сетки (сдвиг оттиска, частичное перекрытие текста);
   - выделение **подписей** как графических объектов и привязка к роли («принял», «проверил»), если это следует из соседней подписи бланка;
   - разбор **нешаблонных рукописных вставок** (дописка индекса `…М`, запись о замене узла) с предложением текста оператору;
   - fallback, когда бланк повреждён, фото кривое или тип документа ещё не заведён в библиотеку шаблонов.
7. **Кросс-проверка с корешком** (нижний блок с «А»): дубли печатных/номерных полей повышают точность идентичности агрегата.
8. **Слияние результатов:** шаблон даёт обязательный каркас полей; ИИ/ICR заполняют «живые» реквизиты; конфликт или низкий confidence → очередь проверки оператором (аналог цифр под штрих-кодом).

#### Ожидаемая точность (ориентир)

| Тип контента | Без дообучения на корпусе | После калибровки + операторский контур |
|--------------|---------------------------|----------------------------------------|
| Печатные поля по шаблону | 90–98% | рабочий уровень |
| Рукописный зав. № / год | 70–90% | рабочий уровень |
| Свободная рукопись в графах | ниже, сильно зависит от почерка | приемлемо только с review |
| Наличие печати / подписи (детекция) | умеренно–высокая | высокая |
| Прочтение текста в печати | нестабильно (смаз, перекрытия) | часто остаётся под контролем оператора |
| Идентификация «чья подпись» | вне MVP | справочник ролей + ручное подтверждение |

#### Риски и ограничения

- разные серии бланков, износ бумаги, почерки, съёмка телефоном;
- похожие кириллические символы (В/B, С/C, У/Y) в индексах вроде `МГВ-1СУ8М`;
- печать поверх текста портит и OCR поля, и чтение оттиска — нужна раздельная обработка слоёв;
- подпись как картинка ≠ юридически значимая электронная подпись: в цифровом паспорте фиксируются **факт, зона, дата скана и подтверждение оператора**, а не криптографическая ЭП бумажного росчерка;
- библиотека шаблонов бланков обязательна, но **недостаточна** — без ICR/vision-слоя система не переживёт реальные заверительные реквизиты и рукописные дописки.

### 2.2. Цифровой аналог паспорта (UI)

**Возможность: высокая.**

Интерфейс повторяет раскладку реального бланка:

- те же строки и зоны (наименование, индекс, код ПС, №, год, корешок);
- поля редактируемые;
- визуальная индикация: «распознано / изменено оператором / расхождение с предыдущей версией»;
- история правок на карточке агрегата.

Сценарий модернизации `МГВ-1СУ8` → `МГВ-1СУ8М`:

1. Повторное фото → OCR предлагает новое наименование/индекс.
2. Система сопоставляет запись по **заводскому номеру** `1160340` (и при необходимости по коду ПС / типу).
3. Diff: изменено только наименование/модель; номер не тронут.
4. Оператор подтверждает → пишется запись в журнал с причиной («модернизация»), датой, наработкой ВС/агрегата.

### 2.3. Сопоставление повторных фото (identity + diff)

**Возможность: высокая**, ключ проектирования — **идентификатор агрегата = заводской номер (+ тип/код ПС при коллизиях)**.

Правила:

- совпал № → обновление существующей карточки, не создание дубля;
- изменились «мягкие» поля (наименование, индекс, примечания) → предложение патча;
- изменился № при том же остальном → алерт «возможная ошибка OCR / подмена»;
- пустой/низкоуверенный № → обязательный ручной ввод до сохранения.

Это прямой аналог «полоски штрих-кода + цифры под ними».

### 2.4. База комплектации ВС и журнал состояния

**Возможность: высокая.** По сути это обычный учёт «что установлено на самолёте»: какой агрегат (с заводским номером и паспортом) стоит на какой позиции, когда его ставили/снимали/модернизировали, с какой наработкой это происходило, и какой была комплектация борта на любую прошлую дату. Такие задачи давно решают системы ТОиР (техническое обслуживание и ремонт) и конфигурационного учёта ВС — здесь та же логика, плюс вход из фото паспортов.

Минимальная модель данных:

- **Воздушное судно** (борт, тип, наработка планера);
- **Позиция установки** (место в комплектации);
- **Агрегат** (зав. №, тип, паспортные поля, ресурс, срок службы);
- **Версия паспорта** (снимок полей на момент времени);
- **Событие изменения** (кто, когда, что, почему, наработка на момент, источник: OCR / ручной ввод / импорт);
- **Документ-фото** (файл + результат распознавания + confidence).

Требования к аудиту: append-only журнал (не затирать историю), возможность восстановить состояние ВС «на дату».

### 2.5. Выгрузки, анализ, рекомендации

**Возможность: высокая** для проверок по заранее заданным правилам; **средняя** для прогнозов «что сломается раньше срока», пока нет длинной истории отказов и замен по парку.

Первый этап — не «угадывание нейросетью», а **жёсткие правила** из нормативов и справочников:

- истёк назначенный срок службы;
- наработка ≥ межремонтного / назначенного ресурса;
- отсутствует паспорт / не подтверждён оператором;
- агрегат снят/установлен без закрытия события;
- несовместимость индекса с позицией (по справочнику).

Выход: подсветка проблем, список рекомендуемых действий (замена, продление, проверка документации), отчёты по заранее заданным алгоритмам.

**Прогнозы на основе машинного обучения (ML)** — это уже второй, необязательный контур: модель по накопленной статистике (наработка, типы отказов, условия эксплуатации) оценивает, например, *вероятность*, что агрегат откажет раньше норматива, или рекомендует заранее вывести его в ремонт. Без большой и размеченной истории по парку такие прогнозы ненадёжны; для старта проекта они не нужны. На автономном ПК это **не добавляет** требований к GPU сверх контура распознавания паспортов.

## 3. Стек (рекомендация для MVP)

| Слой | Вариант |
|------|---------|
| Клиент | Web (React/Vue) + адаптив под планшет оператора |
| API | Python (FastAPI) или Node — удобно стыковать с OCR |
| OCR / vision | Только локальные модели: PaddleOCR / Tesseract + ROI-шаблоны; ICR; document-vision для печатей/подписей. Облачные API в автономной версии **не используются** |
| Хранение | PostgreSQL + локальное файловое/объектное хранилище фото (MinIO или каталог на диске) — всё на той же машине или в закрытом LAN |
| Правила | таблица правил + планировщик проверок |
| Auth / роли | оператор, инженер, аудитор, админ |
| Поставка | офлайн-инсталлятор: приложение, БД, веса моделей, справочники — без скачивания из Интернета при установке |

Автономный контур (изолированный ПК / закрытая сеть без Интернета) — **основной целевой режим**, не опция. Все нейросетевые компоненты работают локально на CPU или GPU этой машины.

## 4. Автономная версия и требования к аппаратной части

### 4.1. Что именно нагружает железо

| Задача | Нужна ли нейросеть | Нагрузка |
|--------|--------------------|----------|
| UI, БД, журнал, правила ресурса/срока | нет | обычный ПК |
| Печатный OCR по шаблону | лёгкая модель / классический OCR | CPU достаточно; GPU ускоряет |
| Рукопись (ICR), дописки | да | CPU медленно; GPU желателен |
| Печати, подписи, «живые» реквизиты (vision) | да | **основной потребитель видеопамяти** |
| Обучение/дообучение моделей на новых бланках | да, тяжелее | лучше отдельная станция; на рабочий ПК оператора не обязательно |

На изолированном компьютере оператора нужна мощность для **распознавания** (прогон готовых моделей), а не для обучения. Новые веса при необходимости готовят вне контура и переносят на носителе по регламенту ИБ.

### 4.2. Профили железа

Ориентиры для **одного автономного рабочего места** (приложение + распознавание + БД на одной машине). Важны объём видеопамяти (VRAM) и поддержка CUDA (для стека на NVIDIA — наиболее зрелый путь под локальный OCR/vision). Конкретные артикулы GPU ниже — **класс**, не привязка к одной модели года выпуска.

#### A. Минимальный (только CPU, без дискретной видеокарты)

| Компонент | Рекомендация |
|-----------|--------------|
| CPU | 8 ядер / 16 потоков (класс Intel Core i7 / AMD Ryzen 7 и новее) |
| RAM | 32 ГБ |
| Диск | SSD 1 ТБ (ОС + приложение + модели + фото) |
| GPU | встроенная графика |

**Когда уместно:** пилот, единицы документов в час, упор на шаблонный OCR и ручной ввод. Vision по печатям/подписям будет медленным или урезанным. Как целевой профиль эксплуатации **не рекомендуется**.

#### B. Рабочий (рекомендуемый для автономного места)

| Компонент | Рекомендация |
|-----------|--------------|
| CPU | 8–12 ядер (i7 / Ryzen 7 или workstation-эквивалент) |
| RAM | **64 ГБ** |
| Диск | SSD NVMe **2 ТБ** |
| GPU | **NVIDIA 12–16 ГБ VRAM** (класс RTX 4070 / 4070 Ti / RTX A4000) |

**Зачем GPU:** ICR и document-vision за секунды, а не десятки секунд. 12 ГБ VRAM обычно хватает для локального OCR + средних vision-моделей при обработке **одного документа за раз**.

#### C. Усиленный (очередь с нескольких мест или тяжёлые модели)

| Компонент | Рекомендация |
|-----------|--------------|
| CPU | 12–16+ ядер |
| RAM | 64–128 ГБ |
| Диск | SSD NVMe 2–4 ТБ |
| GPU | **NVIDIA 24 ГБ VRAM** (класс RTX 4090 / RTX A5000) |

**Когда нужно:** несколько операторов шлют фото на один сервер распознавания, либо используются более крупные multimodal-модели.

#### D. Станция подготовки моделей (вне «воздушного зазора»)

Отдельная машина для калибровки/дообучения на корпусе фото. Результат — файлы весов для переноса в автономный контур. Ориентир: GPU **16–24+ ГБ**, RAM 64 ГБ. На ПК оператора в изоляции этот класс не обязателен.

### 4.3. Прочие требования автономной версии

- **Съём фото:** кабель/USB, локальный сканер; без облачной синхронизации камеры.
- **Резервное копирование:** второй диск или съёмный носитель (БД + фото + журнал).
- **Обновления:** офлайн-пакеты (приложение + модели + справочники) на носителе по регламенту ИБ; версия пакета фиксируется в акте.
- **ИБ:** без автообновлений из Интернета; драйвер GPU и ОС — из офлайн-пакета.
- **Схема «один GPU на контур»:** видеокарта нужна на **сервере распознавания**; клиентские ПК/планшеты в закрытой LAN могут быть обычными.

### 4.4. Практический вывод по железу

| Сценарий | GPU | Вердикт |
|----------|-----|---------|
| Демо / отладка шаблонов | нет (CPU) | допустимо |
| Автономное рабочее место в эксплуатации | **12–16 ГБ VRAM** | **целевой минимум** |
| Нагрузка / тяжёлый vision | 24 ГБ VRAM | запас на рост |
| Обучение моделей | 16–24+ ГБ, отдельно | не на месте оператора |

Итог: нейросеть **не обязана** стоять на каждом ПК в цехе — достаточно одного автономного сервера с GPU в закрытом контуре.

## 5. Этапы внедрения

### Этап A — MVP (доказательство ценности)
- 1–3 типа бланков (включая МГВ-1СУ*);
- загрузка фото → распознавание зон → форма цифрового паспорта;
- ручная правка оператором;
- сохранение агрегата и простой журнал изменений;
- привязка к одному ВС и список «истёк срок / ресурс»;
- установка и прогон **без доступа в Интернет** (офлайн-пакет моделей).

### Этап B — эксплуатация
- библиотека шаблонов бланков + детекция печатей/подписей и разбор свободной рукописи;
- diff повторных сканов и сценарий модернизации;
- полная комплектация борта, наработка, отчёты;
- роли и аудит;
- регламент офлайн-обновлений и резервного копирования.

### Этап C — аналитика
- расширяемый набор алгоритмов выгрузки;
- дашборд состояния ВС;
- интеграции с существующими АСУ ТОиР / 1С / Excel-реестрами **внутри закрытого контура** при необходимости.

## 6. Оценка сложности по блокам

| Блок | Сложность | Комментарий |
|------|-----------|-------------|
| UI цифрового паспорта «как на бумаге» | низкая–средняя | вёрстка + форма |
| OCR печатных полей по шаблону | средняя | нужна библиотека бланков |
| ICR рукописи (номер, дописки) | средняя–высокая | обязательно с ручным контуром |
| Печати и подписи (детекция / частичное чтение) | высокая | vision-слой + review; не путать с ЭП |
| Автономная поставка (без Интернета) | средняя | офлайн-инсталлятор, пакет моделей, обновления на носителе |
| Identity + diff модернизаций | средняя | чёткие правила ключа |
| БД комплектации + история | средняя | стандартный domain model |
| Правила ресурса/срока | низкая–средняя | при наличии нормативов в справочниках |
| Прогнозы по статистике (необязательно) | высокая | только после данных и экспертов |

Критические зависимости от заказчика (без них система останется «фотоархивом»):

1. Справочники: типы агрегатов, нормы ресурса/срока, допустимые индексы после модернизации.
2. Корпус размеченных фото паспортов (десятки–сотни на тип бланка), включая разметку рукописи, печатей и зон подписей.
3. Регламент: кто подтверждает изменения, как фиксируется наработка в момент события.
4. Требования ИБ / закрытого контура: изолированный ПК или LAN, порядок переноса обновлений и резервных копий, допустимые модели GPU/ОС.
5. Выбор профиля железа (рабочий 12–16 ГБ VRAM или усиленный 24 ГБ) под поток документов.

## 7. Риски и как их закрывать

| Риск | Митигация |
|------|-----------|
| Ошибки OCR по рукописи | confidence + обязательный review; дубль с корешка |
| Печати поверх текста / нечитаемые оттиски | отдельный слой детекции печати; фиксировать факт наличия, текст — по возможности |
| Ложная «уверенность» vision-ИИ | шаблонный каркас обязательных полей + пороги confidence + очередь оператора |
| Дубли агрегатов | уникальный ключ зав. № (+ тип); поиск похожих |
| Разнообразие бланков | реестр шаблонов, версия шаблона на документ, fallback vision при неизвестном бланке |
| Нет Интернета / устаревание моделей | офлайн-пакеты обновлений; версионирование весов; станция калибровки вне контура |
| Слабое GPU / только CPU | урезанный vision, больше ручного ввода; заранее зафиксировать профиль B как целевой |
| Юридическая значимость | ЭЦП/роль подтверждения цифрового события, неизменяемый аудит, хранение исходного фото (не подмена бумажной подписи) |
| Сопротивление операторов | UX «как бумажный паспорт», минимум кликов, работа без «облака» |

## 8. Итоговый вывод

Система **технически и организационно реализуема** как контур:

**фото паспорта → гибрид (шаблон + OCR/ICR + vision) → цифровая карточка с ручным контролем → конфигурация ВС с полной историей → правила контроля ресурса и срока** — в том числе на **изолированном компьютере без Интернета**.

Образец МГВ-1СУ8 хорошо задаёт шаблонный каркас (вёрстка, печатные якоря), но в эксплуатации к нему добавляются рукописные дописки, печати и подписи — их закрывает локальный vision/ICR-слой под контролем оператора. Сценарий «модернизация изменила название, номер тот же» — штатный случай identity/diff, не исследовательская задача.

Для автономной версии целевое железо рабочего места/сервера распознавания: **CPU 8+ ядер, RAM 64 ГБ, SSD 2 ТБ, GPU NVIDIA 12–16 ГБ VRAM** (усиленный вариант — 24 ГБ). Без дискретной видеокарты система возможна, но с заметной потерей скорости и качества разбора печатей, подписей и рукописи.

Главное условие успеха: **не обещать полную автономность распознавания**, а строить процесс как у штрих-кода — машина предлагает (в т.ч. по нешаблонным реквизитам), оператор подтверждает и при необходимости исправляет; база и аналитика опираются на подтверждённые данные.
