# Техническое задание на минимально работоспособный прототип (MVP) «otchetTK»

**Система автоматизированной экспертизы технологических карт технического обслуживания авиационной техники с применением большой лингвистической модели (LLM)**

Версия: 1.0 (MVP)
Статус: на согласовании

---

## 1. Общие сведения

### 1.1. Наименование

Прототип программного средства автоматизированной экспертизы технологических карт — рабочее наименование **otchetTK**.

### 1.2. Назначение

Прототип предназначен для автоматизированной проверки текста технологических карт (далее — ТК) технического обслуживания авиационной техники на предмет качества описания работ и формирования отчёта с замечаниями, привязанными к конкретным фрагментам проверяемого текста.

Прототип выполняет роль **автоматического рецензента первого прохода**: он формирует перечень замечаний для эксперта-человека. Окончательное решение о качестве ТК и о принятии/отклонении каждого замечания принимает эксперт. Прототип не является средством утверждения документации.

### 1.3. Цель создания MVP

1. Продемонстрировать заказчику принципиальную работоспособность подхода: экспертиза ТК по рубрикатору проверок с генерацией отчёта.
2. Отработать архитектуру «цепь промптов» и форматы данных, пригодные для последующего промышленного развития.
3. Обеспечить в архитектуре возможность последующего перехода с внешних API на локальные модели с открытыми весами без переработки логики проверок.

## 2. Термины и сокращения

| Термин | Определение |
|---|---|
| ТК | Технологическая карта — документ, описывающий последовательность операций при выполнении работ на авиационной технике |
| РЭ | Руководство по технической эксплуатации — документ, в котором изложены в том числе меры безопасности при работе на авиационной технике |
| LLM | Большая лингвистическая (языковая) модель — генеративная нейросетевая модель обработки текста |
| Цепь промптов | Архитектура, при которой экспертиза выполняется последовательностью отдельных формализованных запросов (промптов) к LLM, где каждый запрос решает одну узкую задачу, а результаты передаются по конвейеру |
| Рубрикатор проверок | Формализованный перечень видов проверок, выполняемых над текстом ТК |
| Эталонная карта | ТК, признанная экспертами образцовой по стилю изложения; используется как образец при проверке стиля |
| База мер безопасности | Загружаемый в систему структурированный перечень мер безопасности из РЭ с привязкой к системам воздушного судна |
| Замечание | Единица результата экспертизы: указание на дефект текста ТК с цитатой, обоснованием и рекомендацией |
| Ключевой маркер безопасности | Слово или устойчивое словосочетание, обозначающее критическое действие по обеспечению безопасности (обесточить, заземлить, стравить давление, заблокировать, зашвартовать, поставить колодки и т. п.) |

## 3. Входные данные и базы знаний

### 3.1. Проверяемая технологическая карта

- Формат на этапе MVP: текстовый файл (`.txt`, `.md`) или файл `.docx`.
- ТК содержит (в общем случае): наименование работы, условия выполнения, перечень инструмента и материалов, пошаговое описание операций, отметки о контроле.
- Прототип должен сохранять привязку каждого замечания к исходному тексту: номер шага/пункта ТК и дословная цитата.

### 3.2. База мер безопасности (загрузка, позиция 1)

Программа должна предусматривать **загрузку мер безопасности при работе на авиационной технике** (источник — РЭ и иные регламентирующие документы):

- Формат загрузки: структурированный файл (`.md`, `.txt`, `.csv` или `.json`), содержащий записи вида:
  - идентификатор меры (например, номер пункта РЭ);
  - система/вид работ, к которым мера относится (электросистема, гидросистема, топливная система, система управления, грузоподъёмные работы, работы на высоте и т. д.);
  - текст меры;
  - ключевые маркеры безопасности, соответствующие мере (обесточить, заземлить, стравить давление, заблокировать, зашвартовать, поставить колодки и т. п.).
- База пополняема: добавление новых записей не должно требовать изменения кода.
- База используется проверкой Р-3 (см. п. 4.1) для сопоставления «система, на которой ведётся работа → требуемые меры безопасности → наличие в ТК ссылки на них и/или ключевых маркеров».

### 3.3. База эталонных карт (загрузка, позиция 2)

Программа должна предусматривать **загрузку нескольких эталонных ТК с возможностью пополнения базы**:

- Формат: те же форматы, что и проверяемая ТК (п. 3.1); каждая эталонная карта сопровождается минимальными метаданными (тип работ, система, дата добавления).
- Назначение: эталонные карты задают образец стиля изложения. При экспертизе проверяемая ТК сопоставляется с эталонами, и система выдаёт **замечания по стилю изложения** (отклонения от принятой в эталонах структуры шага, глагольных форм, степени детализации, оформления ссылок на РЭ).
- Пополнение базы (добавление новой эталонной карты) выполняется помещением файла в каталог базы и не требует изменения кода.
- На этапе MVP допускается простой механизм выбора релевантных эталонов (по метаданным «тип работ/система»); полнотекстовый семантический поиск — этап развития.

## 4. Функциональные требования

### 4.1. Рубрикатор проверок

Прототип должен выполнять проверки по трём обязательным рубрикам. Каждая рубрика реализуется отдельным звеном цепи промптов (см. раздел 5) и формирует замечания единого формата (см. п. 4.3).

#### Р-1. Последовательность

Проверка логической последовательности и завершённости операций:

- **Парные операции**: всё открытое должно быть закрыто, снятое — установлено, отключённое — подключено, расстопоренное — законтрено, снятое напряжение/давление — восстановлено (если это предусмотрено работой). Обнаружение «незакрытых пар» — замечание.
- **Порядок операций**: подготовительные и обеспечивающие безопасность действия должны предшествовать основным (например, «обесточить» — до работ в электросети; «стравить давление» — до расстыковки трубопроводов). Нарушение порядка — замечание.
- **Разрывы последовательности**: шаг ссылается на состояние, которое не было создано предыдущими шагами (например, «закрыть лючок», который не открывался), — замечание.
- **Завершающие операции**: наличие заключительных действий (контроль отсутствия посторонних предметов, закрытие люков, запись в документации), если они предусмотрены типом работ.

#### Р-2. Визуализируемость

Проверка того, что текст каждого шага позволяет исполнителю однозначно «нарисовать картинку и действие в голове»:

- одно действие в одном шаге (не допускается несколько разнородных действий в одном пункте без явной нумерации);
- конкретный глагол действия вместо расплывчатого («отвернуть 4 винта ключом S8» вместо «обеспечить доступ»);
- объект действия назван явно и с локализацией (обозначение лючка/агрегата, место на воздушном судне);
- заданы количественные параметры там, где они необходимы (моменты затяжки, зазоры, усилия, давления, время);
- отсутствуют неопределённые местоимения без однозначного антецедента («его», «туда», «там же»);
- отсутствует страдательный залог без исполнителя («должно быть проверено» — кем?).

Дополнительный приём проверки (обязателен в MVP): LLM реконструирует по тексту шага сцену и действие («что исполнитель видит и делает») и формулирует вопросы, на которые текст не даёт ответа. Каждый такой вопрос оформляется как замечание рубрики Р-2 с пометкой «текст не позволяет однозначно восстановить действие».

#### Р-3. Меры безопасности

Проверка построена на следующем принципе, отражающем практику разработки эксплуатационной документации:

> Полные формулировки мер безопасности изложены в РЭ. **Не требуется**, чтобы ТК дублировала все меры безопасности, — иначе технология будет перегружена. **Требуется**, чтобы ТК: (а) содержала ссылки на соответствующие разделы/пункты мер безопасности РЭ в зависимости от систем, на которых проводится работа, и (б) содержала в тексте операций ключевые маркеры безопасности в тех местах, где выполняются критические действия.

Соответственно, прототип выполняет:

1. **Определение затрагиваемых систем.** По тексту ТК определяются системы воздушного судна и виды работ (электросистема, гидросистема, топливная система, система управления и т. д.).
2. **Проверка наличия ссылок на РЭ.** Для каждой затронутой системы по базе мер безопасности (п. 3.2) определяется, на какие пункты мер безопасности ТК обязана ссылаться. Отсутствие ссылки — замечание. Наличие ссылки на нерелевантный пункт — замечание.
3. **Проверка ключевых маркеров.** В тексте операций проверяется присутствие ключевых маркеров безопасности, обязательных для данного вида работ: *обесточить, заземлить, стравить давление, заблокировать, зашвартовать, поставить колодки* и т. п. (перечень маркеров берётся из базы мер безопасности и является пополняемым). Отсутствие обязательного маркера перед соответствующей операцией — замечание с высокой критичностью.
4. **Проверка на перегруженность.** Если ТК дословно дублирует объёмные формулировки мер безопасности, которые достаточно указать ссылкой на РЭ, — формируется замечание рекомендательного характера «заменить дублирование ссылкой на пункт РЭ».
5. **Проверка позиции маркера.** Ключевой маркер должен стоять **до** операции, безопасность которой он обеспечивает (пересечение с рубрикой Р-1; замечание выдаётся один раз, с указанием обеих рубрик).

### 4.2. Проверка стиля по эталонным картам

- Из базы эталонных карт (п. 3.3) выбираются релевантные эталоны (по типу работ/системе).
- LLM сопоставляет стиль проверяемой ТК со стилем эталонов: структура шага, глагольные формы (инфинитив/повелительное наклонение — как принято в эталонах), степень детализации, оформление ссылок на РЭ, оформление отметок о контроле.
- Отклонения оформляются как замечания рубрики «Стиль» с указанием фрагмента ТК и примера оформления из эталона.

### 4.3. Генерация отчёта с замечаниями

Результат работы прототипа — отчёт в двух форматах:

1. **Человекочитаемый отчёт** (`.md`): титульная часть (наименование ТК, дата, версия прототипа, использованная модель), сводка по рубрикам (количество замечаний по критичности), перечень замечаний.
2. **Машиночитаемый отчёт** (`.json`) той же структуры — для последующей интеграции и статистики.

Каждое замечание обязано содержать:

| Поле | Содержание |
|---|---|
| `id` | Уникальный номер замечания в отчёте |
| `rubric` | Рубрика: `sequence` (Р-1), `visualization` (Р-2), `safety` (Р-3), `style` (стиль) |
| `severity` | Критичность: `critical` (влияет на безопасность), `major` (искажает выполнение работы), `minor` (качество текста), `recommendation` (рекомендация) |
| `location` | Привязка к тексту ТК: номер пункта/шага и позиция в документе |
| `quote` | **Дословная цитата** из проверяемой ТК (или указание «фрагмент отсутствует» для замечаний о пропуске) |
| `finding` | Формулировка замечания |
| `justification` | Обоснование: ссылка на пункт базы мер безопасности / эталонную карту / правило рубрикатора |
| `recommendation` | Рекомендация по устранению |

Требования к качеству отчёта:

- **Верифицируемость**: поле `quote` программно проверяется на дословное присутствие в тексте ТК; замечания с несуществующей цитатой отбрасываются с записью в журнал (защита от галлюцинаций LLM).
- Замечания сортируются по критичности, затем по расположению в документе.
- В отчёт включается раздел «Не проверялось» — перечень проверок, которые не удалось выполнить (например, база мер безопасности не содержит данных по затронутой системе), чтобы отсутствие замечаний не воспринималось как подтверждение качества.

## 5. Архитектура: цепь промптов

### 5.1. Принцип

Экспертиза выполняется **не одним обращением к LLM, а цепью специализированных промптов-вопросов**, где каждое звено решает одну узкую задачу и возвращает структурированный ответ (JSON). Такой подход обеспечивает:

- воспроизводимость и отлаживаемость (каждое звено тестируется отдельно);
- контроль галлюцинаций (узкая задача + обязательные цитаты);
- независимость логики проверок от конкретной LLM (см. раздел 6).

### 5.2. Состав цепи (MVP)

```
[ТК, база мер безопасности, эталонные карты]
        │
        ▼
П-0. Структуризация ТК
     «Разбей текст ТК на нумерованные шаги; для каждого шага выдели:
      действие (глагол), объект, локализацию, параметры, ссылки на документы»
     → JSON-структура ТК
        │
        ▼
П-1. Определение контекста работ
     «По структуре ТК определи: системы ВС, на которых ведётся работа;
      вид работ; критические действия»
     → перечень систем и видов работ
        │
        ├──────────────┬──────────────┬──────────────┐
        ▼              ▼              ▼              ▼
П-2. Рубрика Р-1   П-3. Рубрика Р-2   П-4. Рубрика Р-3   П-5. Стиль
 Последователь-     Визуализируе-      Меры безопас-      Сопоставление
 ность: парные      мость: пошаговая   ности: сопостав-   с релевантными
 операции, поря-    оценка + рекон-    ление с базой мер  эталонными
 док, разрывы       струкция сцены     (ссылки на РЭ,     картами
                    и действия         маркеры, перегру-
                                       женность)
        │              │              │              │
        └──────────────┴──────┬───────┴──────────────┘
                              ▼
П-6. Агрегация и дедупликация
     «Объедини замечания, устрани дубли, присвой критичность
      по заданной шкале, отсортируй»
        │
        ▼
Программная верификация цитат (без LLM)
        │
        ▼
[Отчёт .md + .json]
```

### 5.3. Требования к звеньям цепи

- Каждое звено — отдельный промпт с фиксированным шаблоном; шаблоны промптов хранятся в файлах проекта (не «зашиты» в код) и подлежат версионированию.
- Каждое звено обязано возвращать ответ в заданной JSON-схеме; ответ, не прошедший валидацию схемы, автоматически перезапрашивается (не более 2 повторов), затем фиксируется как ошибка звена в разделе отчёта «Не проверялось».
- Температура генерации — 0 (или минимально доступная у провайдера) для воспроизводимости.
- Каждое замечание, формируемое звеньями П-2…П-5, обязано содержать дословную цитату из ТК (см. п. 4.3).
- Все запросы и ответы LLM журналируются (файл журнала на каждый запуск) — для отладки и последующей научной валидации.
- Звенья П-2…П-5 независимы и могут выполняться параллельно.

## 6. Требования к LLM-подсистеме

### 6.1. Этап MVP: внешние API

- На этапе MVP допускается и предусматривается **передача текста во внешние API** LLM-провайдеров — для анализа и демонстрации программы заказчику.
- На этапе MVP в систему загружаются только **обезличенные/учебные ТК**, не содержащие сведений ограниченного распространения. Это ограничение фиксируется в документации пользователя MVP.
- Ключи API задаются через переменные окружения или конфигурационный файл; ключи не хранятся в репозитории.

### 6.2. Переход на локальные модели с открытыми весами

- Архитектура обязана содержать **слой абстракции LLM-провайдера** (единый программный интерфейс: «текст промпта + параметры → структурированный ответ»).
- Вся логика проверок (цепь промптов, схемы ответов, верификация) не должна зависеть от конкретного провайдера.
- Целевой этап развития — работа с локально развёрнутыми моделями с открытыми весами, находящимися в открытом доступе (семейства Qwen, Llama, Mistral и аналогичные), через совместимый интерфейс (например, OpenAI-совместимый API локального сервера инференса: Ollama, vLLM, llama.cpp-server). В MVP достаточно подтвердить переключение конфигурацией: смена провайдера не должна требовать изменения кода проверок.

### 6.3. Конфигурация

Конфигурационный файл прототипа задаёт: провайдера и модель, параметры генерации, пути к базам (меры безопасности, эталонные карты), каталог отчётов и журналов.

## 7. Нефункциональные требования

| № | Требование |
|---|---|
| 1 | Язык интерфейса, промптов и отчётов — русский |
| 2 | Тип приложения на этапе MVP — консольное приложение (CLI): `экспертиза <файл ТК> → отчёт`; графический интерфейс не входит в MVP |
| 3 | Рекомендуемый стек: Python 3.11+; список зависимостей фиксируется в `requirements.txt` |
| 4 | Воспроизводимость: повторный запуск на той же ТК с теми же базами и той же моделью должен давать согласованный набор замечаний (допускаются различия формулировок; состав замечаний критичности `critical`/`major` должен быть устойчив) |
| 5 | Полнота важнее точности: настройка проверок ориентируется на минимизацию пропуска дефектов; ложные срабатывания допустимы (их отклоняет эксперт) |
| 6 | Журналирование всех обращений к LLM и всех отброшенных (неверифицированных) замечаний |
| 7 | Время экспертизы одной ТК объёмом до 5 страниц — не более 10 минут |

## 8. Тестовые данные и критерии приёмки MVP

### 8.1. Тестовые данные

В составе прототипа поставляются:

1. Не менее **3 тестовых ТК**: одна корректная и не менее двух с преднамеренно внесёнными дефектами известных типов (нарушенная парность операций, отсутствующий ключевой маркер безопасности, отсутствующая ссылка на меры безопасности РЭ, шаг с несколькими действиями, неопределённое местоимение, дублирование объёмных мер безопасности в тексте ТК).
2. Тестовая **база мер безопасности** (не менее 10 записей, не менее 3 систем ВС) с ключевыми маркерами: обесточить, заземлить, стравить давление, заблокировать, зашвартовать, поставить колодки.
3. Не менее **2 эталонных карт** в базе эталонов.

Перечень внесённых дефектов фиксируется в отдельном файле (эталон ответа) для проверки полноты.

### 8.2. Критерии приёмки

| № | Критерий |
|---|---|
| 1 | Прототип принимает ТК в форматах п. 3.1 и формирует отчёт в форматах `.md` и `.json` по схеме п. 4.3 |
| 2 | На тестовых ТК с внесёнными дефектами прототип обнаруживает **не менее 80 %** дефектов из эталонного перечня, при этом все дефекты категории «отсутствует ключевой маркер безопасности» обнаруживаются в **100 %** случаев |
| 3 | Каждое замечание в отчёте содержит дословную цитату, программно подтверждённую в тексте ТК (кроме замечаний о пропуске), и обоснование |
| 4 | Пополнение базы мер безопасности и базы эталонных карт выполняется добавлением файлов без изменения кода |
| 5 | Смена LLM-провайдера (внешний API ↔ локальный OpenAI-совместимый сервер) выполняется изменением конфигурации без изменения кода проверок |
| 6 | На корректной тестовой ТК отсутствуют замечания критичности `critical` |
| 7 | Шаблоны промптов вынесены в файлы проекта и доступны для правки без изменения кода |

## 9. Ограничения MVP и направления развития

**Не входит в MVP** (фиксируется для управления ожиданиями заказчика):

- графический интерфейс пользователя;
- обработка сканированных документов (OCR) и чертежей/иллюстраций;
- семантический (векторный) поиск по базам — в MVP выбор эталонов и мер выполняется по метаданным и ключевым словам;
- проверка фото-/пооперационного контроля (отдельная рубрика следующего этапа);
- интеграция с системами документооборота;
- работа с документами ограниченного распространения (до перехода на локальные модели).

**Направления развития после MVP:**

1. Переход на локальные модели с открытыми весами в защищённом контуре (п. 6.2) и снятие ограничения на конфиденциальные документы.
2. Рубрика проверки операций, подлежащих обязательному (в т. ч. фото-) контролю.
3. Векторная база регламентирующих документов (RAG) для обоснования замечаний ссылками на пункты нормативки.
4. Научная валидация: «золотой набор» ТК с размеченными дефектами, измерение полноты/точности по типам дефектов, согласованность с оценками экспертов (каппа Коэна).
5. Накопление статистики принятых/отклонённых экспертом замечаний для настройки проверок.
