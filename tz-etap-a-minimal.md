# Техническое задание: этап A (MVP)

**Профиль аппаратной части:** минимальный (п. 4.2.A оценки реализуемости) — **только CPU, без дискретной GPU**  
**Режим работы:** автономный (изолированный ПК, **без доступа в Интернет**)  
**Основание:** `ocenka-realizuemosti-pasportov.md`  
**Образец документа:** паспорт малогабаритной гировертикали МГВ-1СУ8 (`6В2.564.002-4ПС2`, зав. № по образцу)

---

## 1. Цель этапа A

Доказать ценность системы на одном автономном рабочем месте:

1. загрузить фото паспорта авиаагрегата;
2. распознать основные поля (с приоритетом шаблонного OCR);
3. показать цифровой аналог бланка и дать оператору исправить ошибки;
4. сохранить агрегат и простой журнал изменений;
5. привязать агрегаты к **одному** воздушному судну;
6. подсветить простейшие проблемы (истёк срок / исчерпан ресурс) по справочнику.

Этап A — **пилот**, не полноценная эксплуатация парка. Тяжёлый vision (печати/подписи), очередь с нескольких мест и прогнозы по статистике — **вне объёма**.

---

## 2. Ограничения профиля железа A

Система **обязана** работоспособно функционировать на конфигурации не хуже:

| Компонент | Требование |
|-----------|------------|
| CPU | ≥ 8 ядер / 16 потоков (класс Intel Core i7 / AMD Ryzen 7) |
| RAM | ≥ 32 ГБ |
| Диск | SSD ≥ 1 ТБ |
| GPU | дискретная видеокарта **не требуется** (допустима только встроенная графика) |
| Сеть | Интернет не используется; работа полностью офлайн |

Следствия для проектирования этапа A:

- все модели распознавания — **локальные**, входят в офлайн-инсталлятор;
- распознавание выполняется на **CPU**;
- допустимое время обработки **одного** фото: до **60 с** (целевое — до 30 с на «чистом» бланке МГВ);
- поток: **единицы документов в час**, без параллельной очереди;
- полный разбор печатей/подписей нейросетью **не входит** в обязательный объём A (см. §5);
- при низкой уверенности OCR оператор **всегда** может ввести/исправить поле вручную (аналог цифр под штрих-кодом).

## 3. Объект автоматизации (в рамках A)

### 3.1. Типы бланков

| № | Тип | Обязательность |
|---|-----|----------------|
| 1 | Паспорт семейства МГВ-1СУ* (по образцу МГВ-1СУ8) | обязательно |
| 2–3 | До 2 дополнительных типов бланков того же класса «паспорт агрегата» | желательно, если предоставлены образцы; иначе — после A |

На этапе A достаточно **одного** полностью настроенного шаблона (МГВ).

### 3.2. Поля цифрового паспорта (обязательный минимум)

| Поле | Источник на бланке | Распознавание на CPU | Ручной ввод |
|------|--------------------|----------------------|-------------|
| Наименование агрегата | печатный текст | да | да |
| Индекс / модель (напр. МГВ-1СУ8) | печать / дописка | да | да |
| Код документа (напр. 6В2.564.002-4ПС2) | печать | да | да |
| Заводской номер | рукопись | да (ICR на CPU или усиленный ручной контур) | **обязателен при низкой уверенности** |
| Год выпуска | смешанный | да | да |
| Примечание оператора | — | нет | да |

### 3.3. Вне объёма полей этапа A (сохраняются только как фото/пометка)

- автоматическое чтение текста в печатях;
- идентификация «чья подпись»;
- полный разбор всех граф многостраничного паспорта сверх титульного блока и корешка.

Оператор может отметить флажками: «печать есть на фото», «подпись есть на фото» — без OCR этих объектов.

## 4. Функциональные требования

### 4.1. Установка и запуск (автономно)

| ID | Требование |
|----|------------|
| F-01 | Поставка офлайн-инсталлятором (приложение + СУБД + веса моделей + шаблон МГВ + пустые справочники). Установка **без** доступа в Интернет. |
| F-02 | После установки система запускается локально (браузер на `localhost` или desktop-оболочка — на выбор реализации). |
| F-03 | Версия сборки, версия моделей и версия шаблона бланка отображаются в интерфейсе «О системе». |

### 4.2. Загрузка и хранение фото

| ID | Требование |
|----|------------|
| F-10 | Загрузка фото паспорта: JPG/JPEG, PNG; размер файла до 20 МБ. |
| F-11 | Исходный файл сохраняется без потери (для аудита). |
| F-12 | К фото сохраняются дата/время загрузки и учётная запись оператора. |

### 4.3. Распознавание (CPU)

| ID | Требование |
|----|------------|
| F-20 | Предобработка: выравнивание/поворот по возможности, базовая нормализация. |
| F-21 | Определение бланка МГВ по печатным якорям (`ПАСПОРТ`, код документа, линия отреза) либо выбор шаблона оператором вручную. |
| F-22 | Извлечение полей по ROI шаблона: наименование, индекс, код ПС, зав. №, год. |
| F-23 | Для каждого поля: распознанное значение + уровень уверенности (или статус «не распознано»). |
| F-24 | При уверенности ниже порога (настраиваемый, по умолчанию задаётся в конфиге) поле подсвечивается как требующее проверки. |
| F-25 | Опционально: сверка зав. № / года с корешком (нижний блок), если зона доступна на фото; расхождение — предупреждение. |
| F-26 | Распознавание **не блокирует** сохранение: оператор может заполнить все поля вручную с нуля. |

### 4.4. Цифровой аналог паспорта (UI)

| ID | Требование |
|----|------------|
| F-30 | Экран карточки визуально повторяет структуру титульного блока образца: наименование, индекс, «ПАСПОРТ», код документа, «на изделие №», год; упрощённый корешок. |
| F-31 | Все поля §3.2 редактируемы. |
| F-32 | Индикация происхождения значения: «распознано» / «исправлено оператором» / «введено вручную». |
| F-33 | Кнопки: «Сохранить», «Отменить», «Повторить распознавание» (для того же фото). |

### 4.5. Идентичность агрегата и повторное фото

| ID | Требование |
|----|------------|
| F-40 | Ключ агрегата: **заводской номер** (+ тип/шаблон бланка при необходимости). |
| F-41 | Повторная загрузка фото с тем же зав. № открывает существующую карточку и показывает **diff** изменённых полей (например, индекс МГВ-1СУ8 → МГВ-1СУ8М). |
| F-42 | Сохранение изменений создаёт запись в журнале с причиной (выбор: «модернизация» / «исправление ошибки» / «первичный ввод» / «прочее»). |
| F-43 | Если зав. № пуст или не подтверждён — сохранение новой карточки запрещено до ввода номера оператором. |

### 4.6. Одно ВС и комплектация (упрощённо)

| ID | Требование |
|----|------------|
| F-50 | В системе заводится **одно** воздушное судно (борт, тип — текстовые поля; наработка планера — число). |
| F-51 | Агрегат можно привязать к ВС и к текстовой «позиции установки» (строка; справочник позиций — опционально). |
| F-52 | Список агрегатов борта: номер, индекс, позиция, статус проверки паспорта. |

### 4.7. Журнал изменений

| ID | Требование |
|----|------------|
| F-60 | Append-only журнал: кто, когда, какое поле, старое → новое значение, причина, наработка ВС на момент события (если указана). |
| F-61 | Журнал доступен из карточки агрегата. |
| F-62 | Удаление записей журнала пользователем запрещено. |

### 4.8. Правила подсветки (минимум 5)

| ID | Правило | Действие в UI |
|----|---------|---------------|
| F-70 | Истёк назначенный срок службы агрегата (по справочнику / полю срока) | красная/предупреждающая метка |
| F-71 | Наработка агрегата ≥ назначенного или межремонтного ресурса (если заданы) | метка |
| F-72 | Паспорт не подтверждён оператором после распознавания | метка «требует проверки» |
| F-73 | Агрегат на борту без заводского номера (не должно проходить F-43; контроль целостности) | ошибка |
| F-74 | Индекс не из допустимого списка для типа (если справочник заполнен) | предупреждение |

Справочники срока/ресурса на этапе A могут заполняться вручную администратором (простая таблица). Алгоритмы выгрузки «на заказ» и ML-прогнозы — **вне A**.

### 4.9. Пользователи и роли (упрощённо)

| ID | Требование |
|----|------------|
| F-80 | Не менее двух ролей: **оператор** (распознавание, правка, сохранение) и **администратор** (справочники, пользователи, порог уверенности). |
| F-81 | Вход по логину/паролю (локальная БД учёток). Интеграции с AD/LDAP — вне A. |

## 5. Явно вне объёма этапа A

- дискретная GPU и оптимизация под CUDA;
- полноценный vision-конвейер печатей и подписей (кроме ручных флажков);
- облачные API и любая онлайн-проверка лицензий/моделей;
- несколько ВС / парк / филиалы;
- мобильное приложение (допустим браузер на том же ПК);
- ЭЦП, УКЭП, интеграция с 1С / АСУ ТОиР;
- дообучение моделей на этом же ПК;
- параллельная обработка нескольких фото;
- требования «мягкого реального времени» (&lt; 5 с на документ).

## 7. Модель данных (минимум)

Сущности:

1. **User** — учётная запись, роль.  
2. **Aircraft** — одно ВС (бортовой номер, тип, наработка).  
3. **Component** — агрегат (зав. №, индекс, наименование, код ПС, год, срок/ресурс, статус подтверждения).  
4. **PassportVersion** — снимок полей на момент сохранения.  
5. **DocumentImage** — файл фото, связь с версией/распознаванием, confidence по полям.  
6. **ChangeEvent** — запись журнала.  
7. **Dictionary** — справочники (допустимые индексы, нормы ресурса/срока — упрощённо).

## 9. Порядок работы оператора (сценарии приёмки)

### Сценарий S1 — первичный ввод
1. Войти как оператор.  
2. Загрузить фото паспорта МГВ-1СУ8.  
3. Дождаться распознавания ≤ 60 с.  
4. Проверить/исправить поля, подтвердить зав. №.  
5. Сохранить; запись появляется в списке агрегатов борта.  
6. В журнале — событие «первичный ввод».

### Сценарий S2 — модернизация (смена индекса, номер тот же)
1. Загрузить новое фото того же зав. № с индексом МГВ-1СУ8М (или имитация правкой после OCR).  
2. Система находит карточку, показывает diff по наименованию/индексу.  
3. Оператор подтверждает причину «модернизация».  
4. В журнале — изменение только соответствующих полей; зав. № не менялся.

### Сценарий S3 — ошибка распознавания номера
1. OCR даёт неверный или пустой зав. № (или уверенность ниже порога).  
2. Поле подсвечено.  
3. Оператор вводит номер вручную и сохраняет.  
4. Карточка создаётся/обновляется с пометкой «исправлено оператором».

### Сценарий S4 — подсветка срока
1. В справочнике/карточке задан истёкший срок службы.  
2. В списке борта агрегат помечен предупреждением.

### Сценарий S5 — офлайн
1. На ПК без сетевого подключения выполнить S1.  
2. Убедиться в отсутствии обращений наружу (контроль: сетевой интерфейс отключён / firewall).

## 10. Критерии приёмки этапа A

Этап A считается принятым, если:

1. Система установлена с офлайн-носителя на ПК профиля A и работает **без Интернета**.  
2. На образце (или эквивалентном фото) МГВ отрабатывают сценарии **S1–S5**.  
3. Печатные поля шаблона в среднем распознаются устойчиво на согласованном наборе из ≥ 10 фото (если заказчик предоставляет набор); рукописный номер допускается с ручной коррекцией.  
4. Журнал изменений неизменяем пользователем и содержит историю по S2.  
5. Не менее **5** правил подсветки из §4.8 реализованы и демонстрируются.  
6. Переданы: инсталлятор, краткая инструкция оператора, инструкция резервного копирования, перечень версий ПО/моделей/шаблона.

## 12. Входные данные от заказчика (для старта работ)

1. ≥ 10 фото паспортов МГВ (желательно 30+), по возможности с рукописными номерами.  
2. Реквизиты одного ВС для пилота (борт, тип).  
3. Начальные нормы срока/ресурса хотя бы для МГВ-1СУ8 (или разрешение использовать тестовые значения).  
4. Подтверждение ОС целевого ПК (Windows/Linux).  
5. Назначенные участники приёмки (оператор, администратор).

## 14. Краткая сводка объёма A

| Включено | Не включено |
|----------|-------------|
| 1 ПК, CPU-only, офлайн | GPU, облако |
| 1 шаблон МГВ, ручной контроль OCR | Авторазбор печатей/подписей |
| 1 ВС, журнал, 5 правил | Парк ВС, ML-прогнозы, интеграции |

**Итог:** этап A на минимальном железе — это автономный пилот «фото → поля → цифровой паспорт → журнал → простая подсветка», где нейросеть на CPU помогает по шаблону, а оператор гарантирует корректность заводского номера и правок.
